 ## Persistence (T1053.005)   
 
Hands-on security investigation and multi-layer telemetry analysis of MITRE ATT&CK T1053.005 (Scheduled Task/Job: Scheduled Task). Traced attack execution across local Sysmon host logs, the Windows Security log (Event ID 4698), Microsoft Sentinel SIEM (KQL), and Microsoft Defender XDR, while troubleshooting a missing audit policy and log-routing issues.

## Why Defender did not tag T1053.005, and why this activity is T1053.005  

1. What Defender did?  

Defender XDR raised Incident ID 3, "Suspicious behavior by svchost.exe was observed" (Medium, Active, detection source EDR, service source Microsoft Defender for Endpoint).  
The alert fired about 3 minutes after the test (test at 8:53 PM, incident at 8:56:19 PM), so it was about the test.  
Five processes were listed as evidence, all with verdict Suspicious: powershell.exe, svchost.exe, cmd.exe (PID 12332), schtasks.exe (PID 11412) and powershell.exe.  
Defender auto-tagged T1036 (Masquerading), T1055 / T1055.012 (Process Injection / Hollowing) and T1569.002 (Service Execution). Category: Execution.  
T1053.005 was not tagged, even though the command line is a textbook match.  

2. What this means?  

The alert fired correctly, so detection worked.  
The technique classification was imprecise. Detection and classification are two separate things.
The schtasks.exe file verdict was Suspicious, but the VirusTotal ratio was 0/71 and no malware was detected. So this was a behavioral detection, not a signature one.   schtasks.exe is a legitimate signed Microsoft binary, flagged for how it was used.  

3. Why Defender might not have tagged it (possible reasons, not proven)?  

The alert is named after svchost.exe. The Task Scheduler service ("Schedule") runs inside svchost.exe, and when schtasks.exe creates a task it hands the request to that service. This is normal Windows behavior and not the technique itself.  
The Atomic Red Team PowerShell wrapper may look like masquerading or injection to Defender's heuristics. That would explain T1036 and T1055.  
I cannot confirm either reason from the alert alone. The evidence only shows that the alert fired and did not tag T1053.005.  

4. Why this is T1053.005 anyway:-  

MITRE defines T1053.005 as an adversary using Windows Task Scheduler to run code at a set time, at logon or at startup.  
The technique is the creation of the task, not the svchost.exe process.  
svchost.exe appearing is not the proof, because it would look the same for an admin creating a legitimate task.  

5. Proof, point by point:-  

Sysmon Event ID 1: Image is schtasks.exe with /create, /tn (task name), /sc (trigger) and /tr (the action).  
schtasks /create /tn "T1053_005_OnLogon" /sc onlogon /tr "cmd.exe /c calc.exe"  
schtasks /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"  

Process lineage: powershell.exe → cmd.exe (PID 12332) → schtasks.exe (PID 11412 and 14008), chained with &, run by CYBER\Administrator at High integrity from AppData\Local\Temp.  

Security Event ID 4698: Windows itself logged "A scheduled task was created" for both tasks.  
The task XML shows LogonTrigger and BootTrigger.  
The action is cmd.exe /c calc.exe.  
The OnStartup principal is S-1-5-18 (SYSTEM).  
This needed the audit policy "Other Object Access Events" enabled first.  

The artifact exists: Get-ScheduledTask -TaskName "T1053_005_*" showed both tasks in the Ready state, so persistence was actually installed.
/ru system: the task runs as SYSTEM, a non-SYSTEM process registering a task that later runs as SYSTEM. This matches the persistence and privilege-escalation purpose of the technique.  

Sentinel: both task creation events arrived at 9/22/2026 9:54:16 to 9:54:17 PM UTC, so the same evidence is available in the SIEM.  
Defender device timeline: the same chain appears independently (8:53:19 cmd.exe, 8:53:20 schtasks.exe creating OnLogon, 8:53:21 schtasks.exe creating OnStartup with /ru system).  

6. Why this proof is strong?  

Sysmon (a host log), the Windows Security log (a native log) and Defender's timeline (an EDR log) are three independent sources showing the same behavior.
None of them depends on Defender's technique tags.

## How a real T1053.005 incident is handled (SOC workflow):-  

Triage & Scope: Review the EDR and SIEM alerts, find every endpoint with the suspicious task, and check the process lineage (powershell.exe → cmd.exe → schtasks.exe) and command-line arguments (for example /ru system).  

Containment: This was done automatically done by the Defender by isolation.  
what was done automatically :-Isolate the affected host through the EDR to cut off any command-and-control connection or lateral movement while keeping forensic artifacts.  

Eradication: Remove the tasks with Unregister-ScheduledTask -TaskName "TaskName" or the Task Scheduler UI, and delete any binaries or scripts left in AppData\Local\Temp.  

Root Cause Analysis: Work out how the attacker got in and ran the command (authentication logs, parent process, phishing artifacts).  

Hardening & Detection Tuning: Make sure Event ID 4698 auditing is enabled on all endpoints, and write or tune rules for anomalous schtasks.exe use, especially /ru system or tasks launching from user-writable folders.
