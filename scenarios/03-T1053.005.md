 ## Persistence (T1053.005)   
 
Hands-on security investigation and multi-layer telemetry analysis of MITRE ATT&CK T1053.005 (Scheduled Task/Job: Scheduled Task). Traced attack execution across local Sysmon host logs, the Windows Security log (Event ID 4698), Microsoft Sentinel SIEM (KQL), and Microsoft Defender XDR, while troubleshooting a missing audit policy and log-routing issues.

Test Invoke-AtomicTest T1053.005 -TestNumbers 1  

Output of the test  

Executing test: T1053.005-1 Scheduled Task Startup Script SUCCESS: The scheduled task "T1053_005_OnLogon" has successfully been created. SUCCESS: The scheduled task "T1053_005_OnStartup" has successfully been created. Exit code: 0  

## Structure  

```text

My admin PowerShell console
  └─ powershell.exe                  Invoke-AtomicTest T1053.005 -TestNumbers 1
       └─ cmd.exe (PID 12332)        8:53:19 PM
       │    cmd.exe /c schtasks /create /tn "T1053_005_OnLogon" /sc onlogon /tr "cmd.exe /c calc.exe"
       │                & schtasks /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"
       │
       ├─ schtasks.exe (PID 11412)   8:53:20 PM
       │    creates T1053_005_OnLogon    (trigger: /sc onlogon)
       │
       └─ schtasks.exe (PID 14008)   8:53:21 PM
            creates T1053_005_OnStartup  (trigger: /sc onstart, runs as SYSTEM via /ru system)

```

Both tasks run the same action: cmd.exe /c calc.exe

What this confirms:  
•	Parent chain: cmd.exe (PID 12332) → schtasks.exe (two child processes, PID 14008 and 11412) — a single batch command chaining both task creations with & two tasks created:  
o	T1053_005_OnLogon — trigger: /sc onlogon, action: cmd.exe /c calc.exe  
o	T1053_005_OnStartup — trigger: /sc onstart, action: cmd.exe /c calc.exe, running as /ru system  
•	Worth flagging specifically: the OnStartup task is configured to run as SYSTEM, even though it was created by a standard Administrator context.  
That's a real detection relevant detail — a persistence mechanism that also grants itself SYSTEM-level execution on every reboot is more than just "survives reboot," it's persistence with a privilege boost baked in. Worth noting in your write-up as a T1053.005-specific nuance.  
•	All from Users\ADMINI~1\...\Temp\ — matches the Atomic Red Team execution pattern you'd expect.

But here look clearly it is deletion remember in the below steps I had closed the PowerShell window by mistake and auditing was not enabled so I had to do the cleanup again and again had to load this atomic test .  

So, we are seeing here is the process getting deleted see properly.

look closely at the CommandLine field on this specific event:  

schtasks /delete /tn "T1053_005_OnStartup" /f  

This is a deletion, not creation — this is your -Cleanup step removing the tasks, not the original attack simulation. You can see it clearly in ParentCommandLine too:  

"cmd.exe" /c schtasks /delete /tn "T1053_005_OnLogon" /f >nul 2>&1 & schtasks /delete /tn "T1053_005_OnStartup" /f >nul 2>&1  

That's the cleanup command chaining both deletions with &, same pattern as creation but in reverse.  

To find the actual creation events, scroll further down the list (or filter) for CommandLine containing /create instead of /delete — look for something like:  

schtasks /create /tn "T1053_005_OnLogon" /sc onlogon /ru "..." /tr "cmd.exe /c calc.exe" /f  

click refresh and click find and type /create

What this event shows:  
CommandLine: schtasks /create /tn "T1053_005_OnStartup" /sc onstart /ru system /tr "cmd.exe /c calc.exe"  
•	/ru system — this is the SYSTEM-privilege detail you flagged all the way back at the start, now visible directly in the command line rather than inferred from the SID (S-1-5-18) like it was in the 4698 event.  
•	ParentImage: cmd.exe, ParentProcessId: 8244 — same parent process lineage you saw in your very first Sysmon query, confirming this is the same execution chain.  
•	ParentCommandLine shows the full &-chained batch — both the OnLogon and OnStartup task creations in one command, same as your original notes described.  
•	User: CYBER\Administrator, IntegrityLevel: High — confirms the task was created by an admin-level (not yet SYSTEM) process, which is what makes the /ru system flag meaningful: a non-SYSTEM process is registering a task that will later run as SYSTEM. That's the privilege-boost nuance.
