# Defense Evasion (T1036.005)  

Hands-on security investigation of MITRE ATT&CK T1036.005 (Masquerading: Match Legitimate Name or Location). Simulated by copying a legitimate, signed Windows binary (calc.exe) to a user profile folder under the name Notepad.exe, then traced the execution through local Sysmon host logs (Event ID 1) and compared how Microsoft Defender handled it.   

---

## Test

Invoke-AtomicTest T1036.005 -TestNumbers 1  

Output of the test:  

PS C:\Users\administrator> Invoke-AtomicTest T1036.005 -TestNumbers 1
PathToAtomicsFolder = C:\AtomicRedTeam\atomics

Found 0 atomic tests applicable to windows platform for Technique T1036.005

The Atomic Red Team library has no Windows tests for T1036.005, so nothing ran. Because of this, the technique was simulated manually with a native utility.  

## Manual simulation

Copy-Item "C:\Windows\System32\calc.exe" -Destination "C:\Users\administrator\Notepad.exe"  
Start-Process "C:\Users\administrator\Notepad.exe"    

An attacker masquerades a file by renaming or copying a legitimate tool or payload so it looks like a standard system binary. Here a calculator binary (calc.exe) was copied to a user profile folder and named like a text editor (Notepad.exe).  

Result: Calculator popped up. It ran from the copied name Notepad.exe, which is a visual demonstration of masquerading: a utility made to look like something else to deceive analysts or security controls.

## Structure

```text

My admin PowerShell console (PID 4192)
  └─ Copy-Item  C:\Windows\System32\calc.exe  ->  C:\Users\administrator\Notepad.exe   (file copy)
  └─ Start-Process  C:\Users\administrator\Notepad.exe
       └─ Notepad.exe (PID 1344)   <- really calc.exe
            Image:            C:\Users\administrator\Notepad.exe
            OriginalFileName: CALC.EXE

```

Two commands: one file copy and one process launch. No registry change, no persistence, no network activity. The only artefact is a mismatch between the file name on disk and the file's internal metadata, plus a system binary running from a user profile folder.

## Stage A: SYSMON FINDINGS - Sysmon logs in Event Viewer

For this technique the key event is Event ID 1 (Process Create), because the evidence is in the process's metadata.

## What this confirms  

Image: C:\Users\administrator\Notepad.exe  
Description / Product: Windows Calculator / Microsoft Windows Operating System  
OriginalFileName: CALC.EXE  
CommandLine: "C:\Users\administrator\Notepad.exe"  
Parent: powershell.exe (PID 4192), interactive admin session (TerminalSessionId 1), IntegrityLevel High, CYBER\Administrator.  

This is the key proof of Masquerading (T1036.005): the filename on disk (Notepad.exe) contradicts the internal metadata (OriginalFileName: CALC.EXE, Description: Windows Calculator), and it executes out of a user profile directory instead of System32.  

## T1036.005 nuances:- 

Name vs. metadata mismatch is the detection: Image basename != OriginalFileName. Sysmon records OriginalFileName from the PE header's version resource, which is not changed by renaming the file on disk.  
Wrong location: calc.exe and notepad.exe normally live in C:\Windows\System32 (and C:\Windows). A "Notepad.exe" running from C:\Users\... is suspicious on its own.  
The copy keeps its Microsoft metadata: Company, Product and FileVersion all still say Microsoft, so an analyst skimming only those fields could be fooled. The Image path and OriginalFileName are what give it away.  
Hash is the legitimate binary's hash: the file is an unmodified copy of calc.exe, so its hash matches the genuine Microsoft file. Hash-based blocklists and reputation checks will not flag it.  
Real attackers masquerade the other way round too: a malicious payload named svchost.exe, lsass.exe, explorer.exe, etc., placed in Temp, AppData, ProgramData or Public. Same detection logic applies.  
No registry or persistence component: unlike T1547.001 and T1053.005 this test only shows evasion, not autostart.

## Why Defender stayed silent ?

No signature match: Defender signatures look for known malicious hashes, malicious code patterns or blacklisted payloads. calc.exe is a legitimate, cryptographically signed Windows binary. Copying and renaming it leaves it a valid, untampered Microsoft program.  

No behavioral rule fired: Basic Defender antivirus configurations do not quarantine a file just because it has a misleading name. Flagging the metadata mismatch (OriginalFileName vs. file name on disk) in real time needs an advanced EDR/XDR behavioral rule (such as Defender for Endpoint).  

---

## Why this is T1036.005

MITRE defines T1036.005 as an adversary naming or placing a file to match the name or location of a legitimate file or resource, to evade defenders and tools. The technique is the deceptive name/location, not the tool used to create it (Copy-Item here; a script or malware could do the same).  

Proof:-  

Sysmon Event ID 1: Image is C:\Users\administrator\Notepad.exe but OriginalFileName is CALC.EXE and Description is "Windows Calculator".  
Location: executed from the user profile folder, not System32.  
Behavior: launching "Notepad.exe" opened Calculator, which proves the name does not match what actually runs.  
Lineage: powershell.exe (PID 4192), then Notepad.exe (PID 1344), as CYBER\Administrator at High integrity.  

Why this proof is strong: the evidence comes from the binary's own embedded metadata, which the rename did not change, so the contradiction cannot be explained away by a typo or a custom build. The weak side is coverage: Defender gave no independent confirmation, and Sentinel was not checked.

## Stage E: Analysis

### Response

The test required no containment. The copied Notepad.exe in C:\Users\administrator\ is a leftover artefact of the simulation.

### Why True Positive

This is a true positive because the telemetry shows deceptive naming and placement, not normal software behavior:  

Name contradicts metadata: Sysmon Event ID 1 shows Image: C:\Users\administrator\Notepad.exe, but OriginalFileName: CALC.EXE and Description: Windows Calculator. A genuine Notepad would report NOTEPAD.EXE. Renaming a file on disk does not change the metadata inside it, so the mismatch is a reliable sign of masquerading.  
Wrong location: the real notepad.exe and calc.exe live in C:\Windows\System32 (and C:\Windows). A system-binary name running from C:\Users\administrator\ is not how Windows ships these programs.  
Suspicious execution context: it was launched by powershell.exe (PID 4192) at High integrity as CYBER\Administrator, from an interactive admin session. Legitimate users open Notepad from the Start menu or Explorer, not by running a copied binary from a script.  
Behavior contradicts the name: launching "Notepad.exe" opened Calculator. What ran is not what the name claims.  
Defender's silence does not make it benign: the file is an unmodified, signed Microsoft binary, so hash and signature checks pass. The anomaly shows up only in Sysmon metadata, which is why the host telemetry is the proof.  

This is a true positive for the technique, not for malware. The payload is harmless and the activity was my own test. The point is that the same pattern with a malicious payload would look identical in the logs.  
### How a real incident would be handled

Triage and scope: confirm the finding by comparing Image basename against OriginalFileName. Check whether the same name/location pattern appears on other hosts (hunt on OriginalFileName vs Image across the estate).  
Isolate the host: use Defender for Endpoint "Isolate device" if the file is not a known test or admin tool. Isolation cuts network access, so confirm log forwarding is not needed first, or accept the gap (as happened during this lab's isolation).  
Collect evidence: preserve the binary and record its MD5/SHA256 hashes (here MD5=18E5B970EAB39020B7E53AA81C371287). Capture the Sysmon events, the PowerShell history and the process tree (powershell.exe → Notepad.exe).  
Determine what the real file is: compare the hash with the known-good Microsoft file and check the digital signature. In this test the hash matches calc.exe, so it is a harmless copy. In a real case, a mismatch would mean a malicious payload wearing a system name, and the file would go to sandbox or reverse-engineering analysis.  
Trace how it got there: find the file-creation event (Sysmon EID 11, seen at 11:02:53 PM here) and identify the process that wrote it: Copy-Item from PowerShell, a download, a dropper, an archive extraction or a remote copy. Review the PowerShell script-block log to see the exact command and who ran it.  
Check for follow-on activity: look for persistence (Run keys and scheduled tasks, as in T1547.001 and T1053.005), credential access, lateral movement and outbound network connections from the masqueraded process.
Contain and eradicate: delete the masqueraded file, remove any persistence it created, and reset credentials if the account was misused. Return the host to the network only after it is verified clean.  
Prevent and detect: add a detection for OriginalFileName != Image basename, and for system binary names running outside System32/SysWOW64/C:\Windows. Where possible, use application control (AppLocker or WDAC) to block executables from user-writable paths.  

For this lab test, the response was only cleanup: delete the copied Notepad.exe. No containment or credential reset was needed, because the source was my own authorized test.  

### Cleanup:- 

Remove-Item "C:\Users\administrator\Notepad.exe" -Force
