# Discovery (T1082)

Hands-on security investigation of MITRE ATT&CK T1082 (System Information Discovery). Executed the Atomic Red Team test from an admin PowerShell console and traced the execution through the PowerShell console output and local Sysmon host telemetry (Event ID 1). The test is a read-only reconnaissance step: it creates no persistence and changes nothing on the host, so the evidence is the process-creation record, not a changed system state.   

---

## Test 

Invoke-AtomicTest T1082 -TestNumbers 1

Atomic test name: T1082-1 System Information Discovery (platform: Windows, exit code 0).   

---

## Structure 

```text

My admin PowerShell console (PID 4192, session 1)
  └─ powershell.exe                  Invoke-AtomicTest T1082 -TestNumbers 1
       └─ cmd.exe (PID 10600)        9/24 10:49:02 PM
            │  "cmd.exe" /c systeminfo & reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum
            │
            ├─ systeminfo.exe (PID 10644)   10:49:02 PM
            │     dumps host, OS, hardware, patch, network and domain details
            └─ reg.exe                       queries the disk enumeration key
                  (a VM-detection style check; Sysmon event not captured, see open items)

```

One command line, two discovery actions. Nothing is dropped or changed on the host. What the attacker gains is a profile of the machine: OS and build, domain membership, hotfix level, hardware, and whether it is virtualised. The defender's evidence is the process-creation telemetry.

## Time Clarification: Local vs. UTC Timestamp Mapping

Event Viewer's outer time is Local Machine Time (IST / UTC+5:30), whereas the Sysmon UtcTime field in the event body is UTC. 10:49:02 PM IST on 9/24 equals 17:19:02 UTC on 9/24. Always convert before correlating with any cloud or SIEM source.   

| Event | Local Time (IST / UTC+5:30) | UTC | Investigation Context / Status |
| :--- | :--- | :--- | :--- |
| System boot (from `systeminfo` output) | 9:30:28 PM (9/24) | 16:00:28 (9/24) | Host had been up about 1 hour 19 minutes when the test ran. |
| **Sysmon EID 1:** `cmd.exe` (PID 10600) launched | about 10:49:02 PM (9/24) | about 17:19:02 (9/24) | Parent of `systeminfo`. Its own event was not captured, command line known from the child's `ParentCommandLine`. |
| **Sysmon EID 1:** `systeminfo.exe` (PID 10644) launched | 10:49:02 PM (9/24) | 17:19:02.280 (9/24) | `CommandLine: systeminfo`, parent `cmd.exe`. |  

Note on audit policy: Sysmon Event ID 1 is governed by the Sysmon configuration, so no audit-policy change was needed to capture it. Native Windows Event Viewer logs (Security, System) showed nothing alarming for this test, because systeminfo.exe is a signed Microsoft binary and its use is not an error or a policy event. Sysmon is what recorded the execution.

### What this confirms

Parent chain: powershell.exe (admin console) then cmd.exe (PID 10600) then systeminfo.exe (PID 10644).  
The command line (EID 1): systeminfo, launched by a parent whose command line is "cmd.exe" /c systeminfo & reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum. The & chains two commands, so a second discovery action (the registry query) ran straight after.  
Why cmd.exe appears when I typed in PowerShell: Invoke-AtomicTest hands each test's command to cmd.exe /c to execute it. The user action was in PowerShell, but the process tree shows cmd.exe as the direct parent of the tool. Analysts read these parent-child chains closely, because cmd.exe spawning discovery tools is a typical script or hands-on-keyboard pattern.  
Who and how: CYBER\Administrator, IntegrityLevel High, interactive session (TerminalSessionId 1, LogonId 0xa4044), working directory   C:\Users\ADMINI~1\AppData\Local\Temp\. The same Temp working-directory pattern appears in the other Atomic Red Team tests in this lab.  
Signed, genuine binary: systeminfo.exe is a legitimate Microsoft binary (Company Microsoft Corporation, Product Microsoft Windows Operating System). This is living-off-the-land: no malware is needed to profile the host.  
Hashes recorded: Sysmon stores the MD5 and SHA-256 of the binary, which lets an analyst confirm the file is the genuine Windows copy and hunt for the same hash elsewhere.  
Correlation by GUID: the child's ParentProcessGuid {…0f03…} identifies the cmd.exe instance. GUIDs, not PIDs (which get reused), are the reliable way to stitch the chain.    

### T1082 nuances 

No error, no warning, no native alert. Standard Event Viewer logs (System, Application) show nothing for systeminfo. Only process-creation telemetry (Sysmon EID 1, or Security 4688 with command-line auditing) records it. Without that, this step is invisible.  
OriginalFileName shows sysinfo.exe. That is the PE metadata name inside systeminfo.exe. It is normal for the genuine binary. For detection, compare Image against OriginalFileName to catch renamed copies, but do not treat this particular mismatch as suspicious.   
The registry query is the more interesting half. HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum lists the disk devices. The output here was SCSI\Disk&Ven_NVMe&Prod_VMware_Virtual_N, which reveals the host is a VMware VM. Malware commonly checks this to detect sandboxes and virtual machines.   
Noise lesson: systeminfo is also used by administrators and by some management and inventory tools. A single run is low value on its own. It becomes meaningful when combined with other discovery commands from the same account and host in a short window.

## Why this is T1082 ?  

MITRE defines T1082 (System Information Discovery) as an adversary trying to get detailed information about the operating system and hardware, including version, patches, hotfixes, service packs and architecture. The information guides what the adversary does next, for example whether to fully infect the target or run specific actions.    

Proof:- 
Sysmon Event ID 1: systeminfo.exe, CommandLine: systeminfo, run by CYBER\Administrator at High integrity via cmd.exe.  
Parent command line: cmd.exe /c systeminfo & reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum, which is exactly the Atomic Red Team T1082-1 command.  
Console output: the full systeminfo report (OS, build, hotfixes, NIC, domain) plus the registry result, with exit code 0, proves the commands completed and returned the data.  
No malicious file involved: the technique is the gathering of system information, not the tool. Get-ComputerInfo, wmic os, hostname, ver or the registry could return the same facts.  

### Checking for malicious parameters or obfuscation 

A core SOC skill when reviewing suspicious cmd.exe / powershell.exe command lines (Sysmon EID 1, Sentinel KQL results). Applied to this test:  

1. Command-line parameter flags  
Suppression / hidden windows: /c, /k, -W Hidden, -WindowStyle Hidden. Here cmd.exe /c ran the commands once and exited.  
Execution policy bypasses: -ExecutionPolicy Bypass, -NoProfile. Not present in this test.  
Encoded commands: -EncodedCommand / -enc carrying Base64. Not present in this test.  
Command chaining: &, &&, |, ;. Present: systeminfo & reg query …. Chaining several discovery commands in one line is typical of scripted recon.  


2. Obfuscation techniques  
String concatenation or splitting: sys + teminfo, or caret escaping like s^y^s^t^e^m^i^n^f^o.  
Environment variable masquerading: %ComSpec% instead of cmd.exe.  
Case randomization: SyStEmInFo.eXe.

3. Verdict for this test
 
The command line was plain and unobfuscated: no encoding, no hidden window flags, no case tricks. That is typical of a lab simulation. A real attacker may disguise it, so detection should not rely on the literal string alone. Examples to hunt for:

systeminfo or systeminfo.exe spawned by cmd.exe, powershell.exe, wscript.exe, mshta.exe or an Office process  
reg query HKLM\SYSTEM\CurrentControlSet\Services\Disk\Enum (VM detection), plus other checks such as reg query HKLM\HARDWARE\DESCRIPTION\System /v SystemBiosVersion  
wmic os get ..., wmic computersystem get ..., Get-ComputerInfo, Get-WmiObject Win32_OperatingSystem, [Environment]::OSVersion, hostname, ver  
Several of these in one short window from the same account and host (discovery bursts)  
Renamed copies of systeminfo.exe (detect on OriginalFileName as well as Image)  

4. Decode and analyze in a lab

De-obfuscating Base64: copy any -EncodedCommand string into a safe offline tool or a short Python snippet (base64.b64decode(s).decode('utf-16le')) to reveal the plaintext command.  
Trace the parent-child lineage: always read ParentCommandLine. Here it carried the full command, which is how the registry query was identified even though the Sysmon event shown was for systeminfo.exe only.

## Stage E: Analysis

Understand the analysis by looking through these 3 points: Response, Why True Positive, and How would a real incident be handled.  

### Response

The test required no containment: it is read-only and changed nothing on the host. No remediation was needed beyond documenting the telemetry. If the same pattern appeared outside a test, the response would depend on what else the account and host were doing (see below).

### Why True Positive 

The behavior matches the technique definition exactly: native tooling was used to collect OS, hardware, patch, domain and network details.  
It was run by an interactive administrator through PowerShell and CMD with a chained registry query that checks for virtualisation, which goes beyond ordinary inventory use.  
Sysmon recorded the full command line, parent command line, user, integrity level and hashes.  
In this lab it is an intended, simulated action (Atomic Red Team), so the technical classification is a true positive and the business classification is a benign true positive (authorized testing).  

### How would a real incident be handled ? 

Triage. Who ran systeminfo, from which parent, at what time? A single run by an admin during a support call is normal.

Check whether it is legitimate. Is there a ticket, an inventory or management tool that does this, or an admin who normally does it? Contact the user and system owner.

Look at the surrounding activity. Discovery is rarely the goal. Search the same host and account, shortly before and after, for other discovery (T1057 process discovery, T1083 file discovery, T1016 network config, T1033 user discovery), credential access, persistence and lateral movement.

Assess the source. If the parent is unusual (Office app, script host, web shell, remote shell) or the account is not normally interactive, raise the priority.

Contain if it is part of an intrusion. Isolate the device, disable or contain the account, reset credentials if theft is suspected.

Preserve evidence. Collect the Sysmon log, Defender timeline and forwarded SIEM data. Record hashes and command lines.

Escalate. Hand over to the incident response team if the activity is confirmed malicious.

Harden. Enable process-creation auditing with command line (Security 4688) as well as Sysmon, forward logs centrally, and build a correlation rule for several discovery commands from one account in a short window.
