# Discovery (T1057)

Hands-on security investigation of MITRE ATT&CK T1057 (Process Discovery). The Atomic Red Team invocation for T1057 found no applicable Windows test in the local atomics folder, so the technique was executed manually by running the native utility tasklist.exe directly from an admin PowerShell console. Traced the execution through the console output and local Sysmon host telemetry (Event ID 1). Like T1082, this is a read-only reconnaissance step: nothing is planted or changed, so the evidence is the process-creation record and what the output reveals.   

---

## Test 

Invoke-AtomicTest T1057 -TestNumbers 1  

## Result:

PathToAtomicsFolder = C:\AtomicRedTeam\atomics  
Found 0 atomic tests applicable to windows platform for Technique T1057  

Because the automated test did not run, the technique was performed manually with the equivalent native command:

tasklist.exe

## Structure

```text

My admin PowerShell console (PID 4192, session 1)
  └─ tasklist.exe (PID 6388)         9/24 10:49:40 PM
       typed directly in PowerShell, no cmd.exe in between
       lists every running process with PID, session and memory usage

```

Compare with T1082, where the Atomic test wrapped its command in cmd.exe /c and the tool's parent was cmd.exe. Here the command was typed in the console, so the parent is powershell.exe itself. Both are valid chains for process discovery, and a detection should cover both.

### What this confirms ?

Parent chain: powershell.exe (PID 4192) then tasklist.exe (PID 6388). The tool was launched directly from the PowerShell console, with no cmd.exe in between, because it was typed by hand and not run through the Atomic module.   
The command line (EID 1): "C:\WINDOWS\system32\tasklist.exe". PowerShell expanded tasklist.exe to its full path, so the logged command line is the quoted path with no arguments. It lists all processes with default options.  
Who and how: CYBER\Administrator, IntegrityLevel High, interactive session (TerminalSessionId 1, LogonId 0xa4044). This is the same LogonId as the T1082 systeminfo.exe event, which ties both discovery steps to one logon session. The working directory is the user's profile C:\Users\administrator\, not the Temp directory seen in the Atomic tests, which is another hint that this one was typed by hand.
Hard match with the console output: the tasklist output lists tasklist.exe as PID 6388 and powershell.exe as PID 4192 in Console session 1. These match the Sysmon ProcessId and ParentProcessId exactly, so the console output and the log describe the same execution.  
Signed, genuine binary: tasklist.exe is a legitimate Microsoft binary (OriginalFileName tasklist.exe, Company Microsoft Corporation). This is living-off-the-land: no malware is needed to enumerate processes.
Hashes recorded: Sysmon stores the MD5 and SHA-256 of the binary, so the file can be verified as the genuine copy and hunted for elsewhere.  

### T1057 nuances:-

Atomic module vs. manual run. The Atomic invocation did nothing, so the evidence comes from the manual tasklist.exe. State this clearly in any report so no one assumes the Atomic test passed.  
No native warning. Standard Event Viewer logs show nothing for tasklist. Only process-creation telemetry (Sysmon EID 1, or Security 4688 with command-line auditing) records it.  
Process discovery has many equivalents. tasklist is only one: Get-Process, wmic process list, qprocess, query process, tasklist /v, tasklist /svc and direct WMI/CIM queries return the same information. Detection that only matches tasklist.exe is easy to bypass.  
Noise lesson: administrators and monitoring tools use tasklist constantly. Alert on context (unusual parent, unusual account, piped to findstr looking for security tools, or part of a discovery burst), not on the bare command.

## Why this is T1057 ?

MITRE defines T1057 (Process Discovery) as an adversary trying to get information about running processes on a system. The information can show common software and applications running on the host, and it shapes the adversary's next steps, such as whether to fully infect the target or take specific actions. On Windows, tasklist and Get-Process are the usual tools.  

Proof:-  
Sysmon Event ID 1: tasklist.exe, run by CYBER\Administrator at High integrity, parent powershell.exe (PID 4192).  
Console output: the full process list returned by tasklist.exe, including tasklist.exe itself as PID 6388 and the parent powershell.exe as PID 4192, matching Sysmon exactly.  
Same logon session as T1082: LogonId 0xa4044 appears in both the systeminfo.exe and tasklist.exe events, so the two discovery steps came from one session, 38 seconds apart.  
No malicious file involved: the technique is the enumeration of processes, not the tool. Get-Process, wmic process, WMI or direct API calls would be the same technique.

## Checking for malicious parameters or obfuscation

A core SOC skill when reviewing suspicious cmd.exe / powershell.exe command lines (Sysmon EID 1, Sentinel KQL results). Applied to this test:  

1. Command-line parameter flags   
Verbose and service views: tasklist /v (adds user, window title, CPU time), tasklist /svc (services in each process), tasklist /m (loaded modules, useful for spotting injected DLLs). Not used here; the plain command was run.  
Remote targets: tasklist /s <host> /u <user> /p <pass> enumerates processes on another machine. Not used here, but it would signal lateral movement.  
Filtering: tasklist /fi "imagename eq MsMpEng.exe" or | findstr /i "defender sense sysmon splunk" checks for specific security tools. Not used here, but this is the pattern that raises suspicion.  
Hidden windows / encoded commands: -W Hidden, -EncodedCommand. Not present in this test.  

2. Obfuscation techniques  
String concatenation or splitting: task + list, or caret escaping like t^a^s^k^l^i^s^t.  
Environment variable masquerading: %ComSpec% instead of cmd.exe.  
Case randomization: TaSkLiSt.eXe.  

3. Verdict for this test  

The command was plain and unobfuscated: the bare tasklist.exe with no arguments, no filtering and no encoding. That is typical of a lab simulation or a casual admin check. A real attacker may disguise it, so detection should not rely on the literal string alone. Examples to hunt for:  

tasklist.exe with /v, /svc, /m or /s, particularly from a script host, Office process or remote shell  
tasklist | findstr or tasklist /fi naming security products (MsMpEng, MsSense, Sysmon, splunk, nessus, edr, crowdstrike, carbon)  
Get-Process, Get-CimInstance Win32_Process, wmic process list, qprocess, query process  
Process discovery in a burst with systeminfo, whoami, ipconfig, net user, hostname from the same account and logon session  
Renamed copies of tasklist.exe (detect on OriginalFileName as well as Image)  

4. Decode and analyze in a lab  
De-obfuscating Base64: copy any -EncodedCommand string into a safe offline tool or a short Python snippet (base64.b64decode(s).decode('utf-16le')) to reveal the plaintext command.  
Trace the parent-child lineage: always read ParentCommandLine. Here the parent was the interactive PowerShell console, which fits a hands-on-keyboard run.

## Stage E: Analysis  

Understand the analysis by looking through these 3 points: Response, Why True Positive, and How would a real incident be handled.

### Response

The test required no containment: it is read-only and changed nothing on the host. No remediation was needed beyond documenting the telemetry. In a real case the response depends on what else the account and host were doing (see below).

### Why True Positive

The behavior matches the technique definition exactly: a native utility was used to list all running processes.  
It was run by an interactive administrator at High integrity, within a minute of systeminfo from the same logon session, which fits the typical order of an attacker profiling a host.  
Sysmon recorded the full command line, parent, user, integrity level and hashes, and the PIDs match the console output.  
The Atomic Red Team test itself did not run, so this is a manual simulation of the technique. The technical classification is still a true positive for T1057, and the business classification is a benign true positive (authorized testing).  

### How would a real incident be handled


Triage. Who ran tasklist, from which parent, with which arguments, and at what time? A single plain run by an admin is common.

Check whether it is legitimate. Is there a ticket, a monitoring tool or an admin who normally does this? Contact the user and system owner.

Look at the arguments and what followed. Filters for security tools, /s against other hosts, or /m on lsass.exe are stronger signals than the bare command. Check what happened next: an attempt to stop or tamper with the tools that were listed, credential access, persistence or lateral movement.

Look at the surrounding activity. Search the same host and account for other discovery (T1082, T1033, T1016, T1083) and for anything done before it. Discovery is rarely the goal.

Assess the source. An unusual parent (Office app, script host, web shell, remote shell) or a non-interactive account raises the priority.

Contain if it is part of an intrusion. Isolate the device, disable or contain the account, reset credentials if theft is suspected.

Preserve evidence. Collect the Sysmon log, Defender timeline and forwarded SIEM data. Record hashes and command lines.

Escalate and harden. Hand over to incident response if confirmed malicious. Enable command-line process auditing alongside Sysmon, forward logs centrally, and alert on discovery bursts and on process listings that are filtered for security tools.
