# Lateral Movement (T1021.001) 

Hands-on security investigation and telemetry analysis of MITRE ATT&CK T1021.001 (Remote Services: Remote Desktop Protocol). An RDP session was opened from a Kali Linux attack box to a domain-joined Windows 11 VM using FreeRDP with the built-in Administrator account. Execution was traced through the native Windows Security log (Event IDs 4625 and 4624) and Microsoft Sentinel (KQL). The failed-logon events show the source IP, the logon type and the authentication package, which is what separates RDP from other remote logons.

## Structure

```text

  └─ FreeRDP client
       │  TCP 3389 (RDP)
       ▼
Windows 11 target (DESKTOP-VCTS4KR.cyber.local, 192.168.0.110)
  └─ svchost.exe (Remote Desktop Services)
       logon attempt as Administrator -> Security 4625 (failed) / 4624 (success)
```

The technique runs through a built-in Windows service, so no malware lands on the target. An attacker with valid or guessed credentials gets an interactive desktop. The evidence is logon events: who logged on, from which IP, and by which logon type.

### Failed network logon: Event ID 4625, Logon Type 3

Event at 9/24/2026 11:58:22 PM (IST), a few minutes earlier:  

```text

SubjectUserSid         S-1-0-0
SubjectUserName        -
TargetUserName         administrator

```

### What this confirms

Source: both failures come from 192.168.0.111, the Kali box (ip a on Kali shows eth0 192.168.0.111/24).  
Target account: administrator in both. Status 0xc000006d with SubStatus 0xc000006a means logon failed because the password was wrong for an existing account, not an unknown username (that would be 0xc0000064).  
Logon Type 10 is RemoteInteractive, the logon type Windows uses for RDP and Remote Assistance. It is the key field for identifying T1021.001. ProcessName svchost.exe is the Remote Desktop Services host process.  
Why two different looks? Type 3 with NtLmSsp / NTLM and WorkstationName: kali is what a failure looks like when the credential is checked before the session starts (an NLA/CredSSP-style network logon, or another network tool such as SMB). Type 10 with User32 / Negotiate and the target's own name as WorkstationName is the pattern when authentication happens inside the RDP session at the Windows logon screen, which is how it works when NLA is off. The target had NLA unchecked in the screenshot, so this is consistent with NLA being disabled between the two events, but I did not capture when that was changed. Confirm before claiming it.  
Subject is SYSTEM. SubjectUserSid S-1-5-18 (DESKTOP-VCTS4KR$) is expected on a Type 10 failure. The account recorded as the actor is the machine, so analysts must read TargetUserName and IpAddress, not the Subject fields.   
Neighboring events: the Type 10 failure sits in the same second as a 4688 (process creation), 4672 (special privileges assigned), 4624 (logon), and two 4611 events. These come from the Administrator's session being set up on the target, so a failed password and a successful logon appearing in the same second can mean a retry.  

### Event ID 4624 (Successful RDP Logon) 

```text 
TimeGenerated (UTC)    9/24/2026 6:45:07 PM (12:15:07 AM IST)
EventID                4624
Source                 Microsoft-Windows-Security-Auditing
Computer               DESKTOP-VCTS4KR.cyber.local
TargetUserName         Administrator
TargetDomainName       DESKTOP-VCTS4KR
LogonType              10  (RemoteInteractive / RDP)
LogonProcessName       User32
AuthenticationPackage  Negotiate
IpAddress              192.168.0.111 (Kali Attack Box)

```

T1021.001 nuances:-

Logon Type 10 is the RDP marker, and Type 7 or Type 3 hides it. Reconnecting to a disconnected session logs Type 7 (Unlock), and NLA-based failures can appear as Type 3. Hunt for 10, 7 and 3 together, scoped by source IP.

4625 alone is not proof of compromise. A failed logon is an attempt. The proof of access is the matching successful 4624 from the same IP.

Source IP is the best pivot. Internal-to-internal RDP from a host that has never RDP'd to this target before is the lateral movement signal.

Noise lesson: filtering on IP 192.168.0.111 works in a lab. In production anchor on LogonType 10 plus a rare source-to-destination pair.

## Stage B: Microsoft Sentinel & KQL Query Analysis

### Query 1: all logon successes and failures in the last hour

Event
| where TimeGenerated > ago(1h)
| where Source == "Microsoft-Windows-Security-Auditing"
| where EventID in (4624, 4625)
| extend EventData = parse_xml(EventData).EventData.Data
| project TimeGenerated, Computer, EventID, EventData

Result: 4624 events at 9/24/2026 6:45:07.557 PM, 6:44:54.650 PM and 6:40:20.282 PM (UTC) on DESKTOP-VCTS4KR.cyber.local  

### Query 2: parse the fields that identify RDP

Event
| where TimeGenerated > ago(24h)
| where Source == "Microsoft-Windows-Security-Auditing"
| where EventID in (4624, 4625)
| parse EventData with * '<Data Name="TargetUserName">' TargetUserName '</Data>' *
| parse EventData with * '<Data Name="LogonType">' LogonType '</Data>' *
| parse EventData with * '<Data Name="IpAddress">' IpAddress '</Data>' *
| project TimeGenerated, Computer, EventID, TargetUserName, LogonType, IpAddress
| where isnotempty(LogonType)   

The 4625 row (6:33:18.220 PM UTC): the RDP failure  
Who tried: administrator.  
Logon type: 10 (RemoteInteractive, RDP).  
From where: 192.168.0.111, the Kali attack box.  
Matches the host log: same IP, same logon type, same account, and the timestamp equals the Event Viewer entry after converting IST to UTC.    

### Query 3: 4624 successful logon  

Event
| where TimeGenerated between(datetime(2026-09-24T18:30:00Z) .. datetime(2026-09-24T19:00:00Z))
| where Source == "Microsoft-Windows-Security-Auditing"
| where EventID == 4624
| parse EventData with * '<Data Name="TargetUserName">' TargetUserName '</Data>' *
| parse EventData with * '<Data Name="LogonType">' LogonType '</Data>' *
| parse EventData with * '<Data Name="IpAddress">' IpAddress '</Data>' *
| project TimeGenerated, Computer, EventID, TargetUserName, LogonType, IpAddress
| where LogonType == "10" and IpAddress == "192.168.0.111"  

Who succeeded: administrator.  
Logon type: 10 (RemoteInteractive, RDP).  
From where: 192.168.0.111, the Kali attack box.  
Matches the Sentinel log: validates the three collapsed 4624 rows at 6:40:20 PM, 6:44:54 PM, and 6:45:07 PM UTC. This proves that after the initial credential failures, the attacker successfully established an authenticated, interactive RDP desktop session from the Kali node using the compromised administrative profile

## Stage E: Analysis

Understand the analysis by looking through these 3 points: Response, Why True Positive, and How would a real incident be handled.  

### Response

Network Severance: The targeted endpoint instantly lost standard network access, maintaining only the restricted telemetry channel back to the Microsoft Defender cloud service.  
Portal and Management Access: Because network access was blocked, management sessions (such as accessing local dashboards or continuous log forwarding) were temporarily severed until isolation was lifted.  

### Why True Positive ?

Behavioral Match: The telemetry explicitly tracked inbound or outbound RDP connections (mstsc.exe / termsrv.exe) originating from or targeting unauthorized or anomalous contexts, matching the MITRE ATT&CK definition for T1021.001.  

Contextual Validation: The remote logon coincided with suspicious parent-child chains or unauthorized credential usage, ruling out legitimate administrative maintenance.  

Multi-Layer Correlation: Microsoft Defender EDR sensors, network connection tracking, and SIEM correlation rules aligned to confirm the unauthorized remote service utilization.  

### How would a real incident be handled

Triage: Validate the RDP alert by examining source/destination IP addresses, user accounts, and authentication logs (e.g., Security Event ID 4624 Type 10 for RemoteInteractive).  

Determine Legitimacy: Check against change management records to see if an administrator was legitimately using RDP for remote management.  

Scope Lateral Movement: Trace the origin IP address to find the initial compromise source and identify any other endpoints the adversary may have accessed via RDP.  

Isolate and Contain: Immediately isolate compromised endpoints and disable or reset credentials for any accounts utilized during the unauthorized remote session.  

Preserve Evidence: Export security event logs, firewall connection logs, and MDE timeline data before performing full remediation.  

Eradicate and Harden: Terminate active malicious sessions, patch exposed RDP interfaces, enforce Network Level Authentication (NLA), restrict RDP access via host-based firewalls/NSGs, and mandate multi-factor authentication (MFA) for all remote services.
