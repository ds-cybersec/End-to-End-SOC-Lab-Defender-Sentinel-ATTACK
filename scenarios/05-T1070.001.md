# Defense Evasion (T1070.001)

Hands-on security investigation and multi-layer telemetry analysis of MITRE ATT&CK T1070.001 (Indicator Removal: Clear Windows Event Logs). Traced attack execution across local Sysmon host logs (Event ID 1), the native Windows System log (Event ID 104), Microsoft Sentinel SIEM (KQL, Security Event ID 4688) and Microsoft Defender XDR, and observed how Defender's attack disruption responded after the log was cleared.

---

## Test

Invoke-AtomicTest T1070.001 -TestNumbers 1

Underlying command executed by the test: wevtutil cl System

---

## Structure

```text

My admin PowerShell console (PID 11916, opened 3:23:54 AM)
  └─ powershell.exe                  Invoke-AtomicTest T1070.001 -TestNumbers 1
       └─ cmd.exe (PID 6984)         7:42:30 AM
            │  "cmd.exe" /c wevtutil cl System
            │
            └─ wevtutil.exe (PID 11016)   7:42:30 AM
                 clears the System event log -> System Event ID 104 (Log clear)


```
One command, one log cleared. Unlike T1547.001, nothing new is planted on the system (no Run key, no task). Instead, evidence is destroyed: every earlier entry in the System log was deleted. What remains is the clear event itself (Event ID 104) plus the process records from other sources (Sysmon, Security 4688, Defender) that show who ran the command.

## Time Clarification: Local vs. UTC Timestamp Mapping

Timezone reference note: Local host logs (Event Viewer, PowerShell TimeCreated) are in Local Machine Time (IST / UTC+5:30), whereas Microsoft Sentinel indexes everything in UTC. For Sysmon output the outer TimeCreated is local time, while the inner UtcTime in the message body is UTC (7:42:30 AM IST = 02:12:30 UTC).  
The Defender XDR incident pages I captured displayed times in a different timezone again (alert at "Sep 22, 7:12 PM", which equals 02:12 UTC on Sep 23 if the portal was set to UTC-7). Always convert before correlating.

Note on audit policy: Sysmon Event ID 1 is governed by the Sysmon configuration, and System Event ID 104 is written by the Eventlog service itself, so neither needed any audit-policy change. Security Event ID 4688 (process creation) with command line was already being collected by the Sentinel data collection rule.
