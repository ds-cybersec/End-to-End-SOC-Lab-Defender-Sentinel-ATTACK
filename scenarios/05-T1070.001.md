# Defense Evasion (T1070.001)

Hands-on security investigation and multi-layer telemetry analysis of MITRE ATT&CK T1070.001 (Indicator Removal: Clear Windows Event Logs). Traced attack execution across local Sysmon host logs (Event ID 1), the native Windows System log (Event ID 104), Microsoft Sentinel SIEM (KQL, Security Event ID 4688) and Microsoft Defender XDR, and observed how Defender's attack disruption responded after the log was cleared.

---

## Test

Invoke-AtomicTest T1070.001 -TestNumbers 1

Underlying command executed by the test: wevtutil cl System

## Structure

```text
       └─ cmd.exe (PID 6984)         7:42:30 AM
            │  "cmd.exe" /c wevtutil cl System
            │
            └─ wevtutil.exe (PID 11016)   7:42:30 AM
                 clears the System event log -> System Event ID 104 (Log clear)


```
One command, one log cleared. Unlike T1547.001, nothing new is planted on the system (no Run key, no task). Instead, evidence is destroyed: every earlier entry in the System log was deleted. What remains is the clear event itself (Event ID 104) plus the process records from other sources (Sysmon, Security 4688, Defender) that show who ran the command.

## Time Clarification: Local vs. UTC Timestamp Mapping

Timezone reference note: Local host logs (Event Viewer, PowerShell TimeCreated) are in Local Machine Time (IST / UTC+5:30), whereas Microsoft Sentinel indexes everything in UTC. For Sysmon output the outer TimeCreated is local time, while the inner UtcTime in the message body is UTC (7:42:30 AM IST = 02:12:30 UTC).  
The Defender XDR incident pages I captured displayed times in a different timezone again (alert at "Sep 22, 7:12 PM", which equals 02:12 UTC on Sep 23 if the portal was set to UTC-7). Always convert before correlating.

Note on audit policy: Sysmon Event ID 1 is governed by the Sysmon configuration, and System Event ID 104 is written by the Eventlog service itself, so neither needed any audit-policy change. Security Event ID 4688 (process creation) with command line was already being collected by the Sentinel data collection rule.

## What this confirms  

Parent chain: powershell.exe (PID 11916) then cmd.exe (PID 6984) then wevtutil.exe (PID 11016).  
The command line (EID 1): wevtutil cl System. cl is the short form of clear-log; System is the channel being wiped.  
Who and how: CYBER\Administrator, IntegrityLevel High, interactive session (TerminalSessionId 1, LogonId 0x4F5F04), working directory C:\Users\ADMINI~1\AppData\Local\Temp\. The same Temp working-directory pattern appeared in the T1053.005 and T1547.001 tests, which matches Atomic Red Team execution.  
Event correlation by GUID: wevtutil's ParentProcessGuid {…b128…} equals cmd.exe's ProcessGuid {…b128…}, and cmd.exe's ParentProcessGuid {…a526…} is the long-running PowerShell console (PID 11916). Sysmon GUIDs, not PIDs (which get reused), are the reliable way to stitch the chain.  
Speed: cmd.exe at 02:12:30.522 UTC, wevtutil.exe at .599. The chain took under 100 ms, which looks scripted rather than typed.  
Signed, genuine binary: wevtutil.exe is a legitimate Microsoft binary (OriginalFileName wevtutil.exe, Microsoft Corporation). 
This is living-off-the-land: no malware is needed to destroy the evidence.  

## Some things to remember:-

The Sysmon log survives, the cleared log does not. wevtutil cl System wipes only the System channel. The Sysmon Operational log, the Security log and Defender telemetry are separate sources and kept the evidence. This is why you never rely on a single log source.  
Sysmon has no "log cleared" event for this.  
The proof of the act comes from Sysmon EID 1 (the process), and the proof of the result comes from System EID 104. Both are needed.  
Security log clearing is different. Clearing the Security log produces Event ID 1102 in the Security log, whereas clearing any other channel (System, Application, etc.) produces 104 in the System log. Hunt for both.  
Noise lesson: -like "*wevtutil*" is fine for a lab. In production anchor on the clear verb as well (wevtutil cl, clear-log, Clear-EventLog), because wevtutil is also used legitimately for exports and queries.

# Why this is T1070.001 ? 

MITRE defines T1070.001 as an adversary clearing Windows Event Logs to hide the activity of an intrusion. Windows event logs record system, security and application events, and deleting them removes the audit trail. The technique is the clearing of the log, not the tool used to do it (wevtutil.exe here; Clear-EventLog, Remove-EventLog, the Event Viewer "Clear Log" button or malware could do the same).   

Proof for this:-  

Sysmon Event ID 1: wevtutil cl System run by CYBER\Administrator at High integrity, via powershell.exe then cmd.exe then wevtutil.exe.    
System Event ID 104: LogFileCleared, Channel System, SubjectUserName Administrator, ClientProcessId 11016, matching the Sysmon PID exactly.   
Security Event ID 4688 in Sentinel: the same two process creations with full command line, delivered off-host to the SIEM.  
Defender XDR: independently raised "Attempt to clear event log" and "Event log was cleared", both tagged T1070.001, with the process tree traced back to the PowerShell console.  

Sysmon (host telemetry), the native System log (Eventlog service), the Windows Security log forwarded to Sentinel, and Defender's EDR sensor are four separate collection paths that all show the same behavior, and Defender's technique tag agrees with the manual analysis. The PID in the 104 event links the destroyed log to the exact process that destroyed it.

# Checking for malicious parameters or obfuscation  

A core SOC skill when reviewing suspicious cmd.exe / powershell.exe command lines (Sysmon EID 1, Sentinel KQL results). Applied to this test:  

1. Command-line parameter flags

Suppression / hidden windows: /c, /k, -W Hidden, -WindowStyle Hidden run a command and close or run invisibly. Here cmd.exe /c was used to run the command once and exit.  
Execution policy bypasses: -ExecutionPolicy Bypass, -NoProfile. Not present in this test.  
Encoded commands: -EncodedCommand / -enc carrying Base64. Not present in this test.

2. Obfuscation techniques

String concatenation or splitting: p + ower + shell, or caret escaping like c^m^d.exe.  
Environment variable masquerading: %ComSpec% instead of cmd.exe.  
Case randomization: PoWeRsHeLl.eXe.  

3. Verdict for this test

The command line was plain and unobfuscated: cmd.exe /c wevtutil cl System, no encoding, no hidden window flags, no case tricks. That is typical of a lab simulation. A real attacker may disguise it, so the detection logic should not rely on the literal string alone. Examples to hunt for:  

wevtutil cl <channel> and wevtutil clear-log <channel>, including the cl flag appearing after other arguments  
wevtutil el | foreach { wevtutil cl $_ } (enumerate all channels, then clear every one)  
Clear-EventLog -LogName ..., Remove-EventLog  
Get-WinEvent -ListLog * | ForEach-Object { [System.Diagnostics.Eventing.Reader.EventLogSession]::GlobalSession.ClearLog($_.LogName) }  
Renamed copies of wevtutil.exe (detect on OriginalFileName = wevtutil.exe, not just Image)  
Obfuscated launchers such as c^m^d /c w^e^v^t^u^t^i^l cl System  

4. Decode and analyze in a lab

De-obfuscating Base64: copy any -EncodedCommand string into a safe offline tool or a short Python snippet (base64.b64decode(s).decode('utf-16le')) to reveal the plaintext command.  
Trace the parent-child lineage: always read ParentCommandLine. The obfuscation is often in the parent script, which then calls a native interpreter to do the work. Here the parent was an interactive PowerShell console.

# Stage E: Analysis  

Understand the analysis by looking through these 3 points: Response, Why True Positive, and How would a real incident be handled.  

## Response  

The test itself did not require any containment, but the device was isolated automatically by Defender for Endpoint attack disruption (see Stage D). Isolation cut all network access from the VM, causing ping to fail with "General failure" and interrupting log forwarding to Sentinel until I released the device from the Action Center. Because the lab exercise was complete, I used Undo on the Isolate device action with a documented reason  

## Why True Positive  

The behavior matches the technique definition exactly: a log channel was deliberately cleared with the native utility wevtutil.exe.  
The clear was run by an interactive administrator through PowerShell and CMD, shortly after a series of other attack-simulation steps. There was no maintenance ticket, no backup of the log (BackupPath empty), and no change window.  
Four independent sources agree (Sysmon, System 104, Security 4688 in Sentinel, Defender), and the PID in the 104 event proves which process caused it.  
Defender raised T1070.001 alerts and correlated them into a human-operated ransomware-style incident.  
In this lab it is an intended, simulated action (Atomic Red Team), so the technical classification is a true positive and the business classification is a benign true positive (authorized testing).  

## How would a real incident be handled  

Triage. Confirm the alert is real: who cleared which log, from which process, at what time. Pivot from the 104 ClientProcessId into Sysmon EID 1 and Security 4688 for the parent chain and command line.

Check whether it is legitimate. Is there a change ticket or scheduled maintenance? Was the log archived first (BackupPath)? Is the account an admin who normally does this? Contact the user and system owner.

Scope the window of blindness. The cleared log is gone, so establish what is missing: everything on that host in that channel before the clear time. Look for the same activity on other hosts, and search Sentinel and Defender for activity before the clear, since that is likely what the attacker wanted hidden.

Hunt for related activity. Look for earlier suspicious process, logon, persistence (T1547/T1053) and privilege-escalation events from the same account and device; also other clears (Security 1102, other channels) across the estate.

Contain. Isolate the device, disable or contain the account, and reset credentials if theft is suspected. Block any associated IPs or URLs.

Preserve evidence. Collect the forwarded SIEM data, the Defender device timeline, the Sysmon log and a memory/disk image before remediation. Record hashes and artifacts as indicators.

Eradicate and recover. Remove malicious components, patch, rebuild the host if its integrity cannot be trusted, and restore logging.

Escalate. Hand over to the incident response team or Microsoft support for forensic analysis if the activity is confirmed malicious.

Harden. Forward logs centrally in near real time; restrict who can clear logs; alert on Security 1102 and System 104; alert on wevtutil cl / Clear-EventLog; enable tamper protection; and monitor for audit-policy changes.
