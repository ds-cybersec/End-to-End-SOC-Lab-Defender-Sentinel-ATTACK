## Persistence (T1547.001)

Hands-on security investigation and multi-layer telemetry analysis of MITRE ATT&CK T1547.001 (Boot or Logon Autostart Execution: Registry Run Keys / Startup Folder). Traced attack execution across local Sysmon host logs (Event ID 1 and Event ID 13), Microsoft Sentinel SIEM (KQL) and Microsoft Defender XDR, and compared how Defender handled this technique against the earlier T1053.005 test.

## Time Clarification: Local vs. UTC Timestamp Mapping

## What this confirms  

•	Parent chain: powershell.exe (PID 11916) then cmd.exe (PID 13872) then reg.exe (PID 12420). Read the output bottom to top to follow execution order, since Get-WinEvent returns newest first.  
•	The registry write itself (EID 13): TargetObject HKU\S-1-5-21-3081539324-20527720-3654862020-500\Software\Microsoft\Windows\CurrentVersion\Run\Atomic Red Team, Details C:\Path\AtomicRedTeam.exe, EventType SetValue, written by C:\WINDOWS\system32\reg.exe as CYBER\Administrator.  
•	The command line (EID 1): REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /V "Atomic Red Team" /t REG_SZ /F /D "C:\Path\AtomicRedTeam.exe". /V is the value name, /t the type, /F forces overwrite and /D is the data, the program that will launch at logon.  
•	IntegrityLevel High, CurrentDirectory C:\Users\ADMINI~1\AppData\Local\Temp\, LogonId 0x4F5F04 and TerminalSessionId 1: an interactive admin session, and the same Temp working directory pattern seen in the T1053.005 test, which matches Atomic Red Team execution.  
•	Event correlation by GUID: the EID 1 for reg.exe and the EID 13 share the same ProcessGuid {ebbcb284-19b9-6ab3-4027-000000002500}, and reg.exe's ParentProcessGuid {…3e27…} equals the ProcessGuid of cmd.exe. Sysmon GUIDs (not PIDs, which get reused) are the reliable way to stitch the chain together.  
•	Speed: cmd.exe started at 00:13:45.452 UTC, reg.exe at .525 and the registry write at .560. The whole chain took roughly 100 ms, which looks scripted rather than typed.  
## Worth flagging specifically (T1547.001 nuances)

•	Legacy technique ID in the Sysmon rule: the EID 13 carries RuleName T1060,RunKey. T1060 was the old ATT&CK ID for Registry Run Keys / Startup Folder, later merged into T1547.001. Sysmon configs can lag behind ATT&CK renumbering, so do not trust the rule name as the final classification.  
•	HKCU shows up as HKU\<SID>: Sysmon logs the key under HKU\S-1-5-21-…-500 (RID 500, the built-in Administrator), not under HKCU. Detection rules must match both forms, or match on the \CurrentVersion\Run path without the hive prefix.  
•	No privilege boost this time: HKCU Run needs no admin rights and executes in the user's own context at that user's logon. HKLM Run would be machine-wide and needs admin. Contrast this with the T1053.005 OnStartup task, which ran as SYSTEM.  
•	The payload path does not exist: C:\Path\AtomicRedTeam.exe is a placeholder, so nothing runs at next logon. In a real intrusion this value would point at a dropped binary or script, often under AppData, Temp, ProgramData or Public.  
•	Noise lesson: a hunt like -match "Run" is fine for a lab but useless in production. Anchor on the registry path, for example -match "CurrentVersion\\Run".  


## Analyzing the Sysmon PowerShell Logs:-

1. The Command That Was Run (Process Create - Event ID 1)  
Event ID 1 (Process Create): This event is specifically engineered to track processes starting. Part of tracking a process birth is knowing its lineage—who spawned it (ParentImage, ParentCommandLine).  

Look at the second block (Id : 1). This shows the exact command that was executed on the computer:  

•	The Command (CommandLine): REG ADD "HKCU\SOFTWARE\Microsoft\Windows\CurrentVersion\Run" /V "Atomic Red Team" /t REG_SZ /F /D "C:\Path\AtomicRedTeam.exe"
•	What it means: The system ran Windows' built-in registry tool (reg.exe) to add a new entry. It told Windows: "Whenever this user logs in, automatically launch the program located at C:\Path\AtomicRedTeam.exe."  
•	Who did it: It was run by cmd.exe (Command Prompt), which was originally opened by PowerShell.    

2.	The Resulting System Change (Registry Value Set - Event ID 13)  
Event ID 13 (Registry Event): This event is engineered to track registry modifications (values set, created, or deleted). Its primary focus is what changed (TargetObject and Details) and which process made the change (Image and ProcessId). Sysmon's schema for registry events simply doesn't include parent fields out-of-the-box.  

Look at the first block (Id : 13). This is Sysmon catching the actual change happening to the Windows Registry:  

•	TargetObject: HKU\...\Software\Microsoft\Windows\CurrentVersion\Run\Atomic Red Team  
•	Details: C:\Path\AtomicRedTeam.exe  
•	What it means: This confirms that the registry key was successfully modified. The shortcut has been successfully written into the user's startup registry folder.  

## Why Event ID 13 Lacks Parent Details ?  

•	Event ID 1 (Process Create): This event is specifically engineered to track processes starting. Part of tracking a process birth is knowing its lineage—who spawned it (ParentImage, ParentCommandLine).  
•	Event ID 13 (Registry Event): This event is engineered to track registry modifications (values set, created, or deleted). Its primary focus is what changed (TargetObject and Details) and which process made the change (Image and ProcessId). Sysmon's schema for registry events simply doesn't include parent fields out-of-the-box.  

## How Analysts Bridge the Gap  

Even though Event ID 13 doesn't print the parent fields directly, you are never left guessing because Sysmon links everything together using IDs and Guids:  
1.	Match the Process ID (ProcessId): Notice that both your Event ID 13 and Event ID 1 share ProcessId: 12420 and ProcessGuid: {ebbcb284-19b9-6ab3-4027-000000002500}.  
2.	Use Event ID 1 as the Map: When you see a registry modification in Event ID 13, you just look at the ProcessId (12420), find the matching Event ID 1 log for that same Process ID, and instantly reveal the full parent history (cmd.exe spawned by PowerShell).  
Think of Event ID 13 as the "crime scene" (what was altered) and Event ID 1 as the "suspect profile" (who did it and how they got there).

## Why this is T1547.001  

MITRE defines T1547.001 as an adversary adding a program to a Run/RunOnce registry key or the Startup folder so it executes automatically when the user logs on. The technique is the creation of the autostart entry, not the tool used to write it (reg.exe here; PowerShell, a script or malware could do the same).  

Proof, point by point  

•	Sysmon Event ID 13: a value was set under \Software\Microsoft\Windows\CurrentVersion\Run, name "Atomic Red Team", data C:\Path\AtomicRedTeam.exe.  
•	Sysmon Event ID 1: reg.exe ADD with /V, /t, /F and /D against the Run key, via powershell.exe, cmd.exe, reg.exe, run by CYBER\Administrator at High integrity from AppData\Local\Temp.  
•	Defender: independently recorded the same chain, the registry change, the ASEP alert and the T1547.001 tag.  
•	PowerShell script content: Defender captured Invoke-AtomicTest T1547.001 -TestNumbers 1 as the origin of the chain.   

Why this proof is strong  

Sysmon (host log), Defender's registry telemetry (EDR) and Defender's script-content capture are separate collection paths showing the same behavior, and Defender's technique tag agrees with the manual analysis. The Windows Security log is the missing third pillar because registry auditing (4657) was not enabled.
